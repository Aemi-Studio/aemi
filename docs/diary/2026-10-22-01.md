# Diary — 2026-10-22 (01)

## Landing the test-support upgrade onto a `main` that had already moved

The 30-commit test-support upgrade (AemiTestKit / AemiTesting) was written against a base from before
`a6446f1` ("Count only the allocations of the thread that measures", ADR 0010). Patches 1–5 applied as they were.
Patch 6, "Count allocations per thread and add a cross-thread allocation window", did not: it makes the counter
per-thread, which `main` already was, and adds `AllocationWindow` on top.

| Question | Probe | Verdict |
|---|---|---|
| Is patch 6's per-thread counting new? | `git am -3` stopped on 4 files, all in the allocation counter | **No.** `main` identifies the counted thread with an atomic `pthread_t` (`adtk_owner`), read with `pthread_equal` inside the hook. The patch does the same with a `uintptr_t`. |
| What is new in it? | Read the diff against `main`'s files | One C entry point, `adtk_malloc_window_begin(thread)`, and the Swift side: a `Measurements` owner flag and `AllocationWindow`. |
| Why does the window need a different lock? | Its `begin` and `end` are separate calls | A `Mutex.withLock` scope cannot span them, so `mallocDelta` now takes an owner flag (`acquire`/`release`) instead. A nested measurement still traps. |

Resolution: `main`'s counter is kept. `adtk_begin_counting(pthread_t)` is factored out so `count_begin` and
`window_begin` share it; `main`'s `minimumAllocations` and its doc comments are kept; the patch's `Measurements` and
`AllocationWindow` are added. The commit message of patch 6 still says the counter *became* per-thread — for
`main` that is only true of the window.

Verified: the allocation suites (12 tests, one intended known issue) and the whole package suite, on this branch.
